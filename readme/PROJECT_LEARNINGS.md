## 💡 작업하면서 깨달은 점

### 1. 데이터 전송과 분석용 수집은 목적이 다르다
- **Lovable → Square:** 가상의 매장 POS 데이터를 준비하는 단계
- **Square·Lovable → BigQuery:** 두 채널의 데이터를 수집하고 통합하는 단계

### 2. 모든 데이터를 Square로 보낼 필요는 없다
공통 상품은 Square에 등록하지만, 주문은 `RETAIL`만 전송한다. `ONLINE` 주문은 Lovable DB에서 직접 수집한다. 통합 분석을 위해 운영 시스템까지 하나로 만들 필요는 없다.

### 3. 분석에 필요한 연결 정보는 원본부터 있어야 한다
매장 주문에 `customer_id`가 없으면 동일 고객의 온라인·오프라인 구매를 연결하기 어렵다. 회원 주문에는 고객 ID를 남기고, 비회원 주문은 별도로 유지한다.

### 4. API 성공만으로 다음 단계가 준비되는 것은 아니다
상품 생성 후에는 원본 상품과 Square의 ID를 연결해서 저장해야 한다. 특히 Item ID와 Item Variation ID를 구분하고, 컬럼에 실제로 어떤 ID가 들어가는지 확인해야 한다.

### 5. 중복 생성 방지와 ID 매핑은 별개다
이미 존재하는 SKU를 건너뛰면 중복 생성은 막을 수 있다. 하지만 원본 CSV에 연결 정보가 없다면, 기존 Square ID를 조회해서 채우는 작업도 필요하다.

### 6. 로컬 CSV 수정은 원본 DB 수정이 아니다
CSV에 sync 정보를 저장해도 Lovable DB에는 반영되지 않는다. 새로 export한 파일로 덮어쓰면 기존 sync 정보가 사라질 수 있으므로 관리 기준이 필요하다.

### 7. 같은 주문을 두 번 집계하지 않아야 한다
Lovable의 매장 주문을 Square에 복사했으므로 양쪽에 같은 거래가 존재한다. 분석에서는 `RETAIL`은 Square, `ONLINE`은 Lovable에서 가져와 중복 집계를 방지한다.

### 8. 현재 필요한 범위부터 구현한다
실패 기록과 복구 처리를 추가할수록 흐름이 복잡해졌다. 현재는 성공 결과 저장을 우선 구현하고, 오류 관리 기능은 이후 확장하기로 했다.

> 데이터를 보내는 것뿐 아니라, 다음 단계에서 연결하고 분석할 수 있는 상태로 남기는 것이 중요하다는 것을 배웠다.
